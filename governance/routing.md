# Model Routing（モデル振り分け）

タスクの複雑度と性質に応じて最適なモデルを選択するためのルーティング表。
サブエージェント起動時（Agentツールの `model` パラメータ）およびセッション開始時のモデル選択に使う。

---

## ルーティング表

| タスクの種類 | モデル | 理由 |
|------------|--------|------|
| ファイル検索・単純なgrep・情報の整形 | haiku | 判断が不要で速度とコストが最優先 |
| 定型的なドキュメント検証（ルーブリック採点） | haiku | 基準が明文化されていれば軽量モデルで十分 |
| 通常のコーディング・バグ修正 | sonnet | 品質とコストのバランスが最良 |
| リサーチ・情報の統合 | sonnet | |
| コードの検証（Verifier役） | sonnet | コードの正確性判定は文書採点より難しい |
| ドキュメント執筆 | sonnet | |
| アーキテクチャ設計・複数ステップの計画 | opus | 下流への影響が大きく、推論の深さが必要 |
| 曖昧な要件の分解・トレードオフ判断 | opus | |
| 長時間稼働するSupervisorセッション | fable | Persistent Agent前提の運用時 |

---

## 運用ルール

1. **デフォルトはsonnet。** 迷ったらsonnetを使い、結果が不十分ならopusに上げる。
2. **ExecutorとVerifierのモデルを揃える必要はない。** opusの成果物をsonnetが検証してよい（基準が明文化されているため）。
3. **同一タスク内でのモデル昇格は1回まで。** haiku→sonnet→opusと段階的に上げ続けるのはコストの無駄。最初から適切なモデルを選ぶ。
4. **opusを使う判断は記録する。** `state/current-task.md` の備考に「opus使用：[理由]」と残し、振り返り時にルーティング表の精度を検証する材料にする。

---

## サブエージェント起動時の適用例

```
Agent(
  subagent_type: "general-purpose",
  model: "haiku",              # ← このルーティング表に基づいて指定
  prompt: "[検証者テンプレート + 成果物]"
)
```

---

## 見直しのタイミング

- ルーティングどおりに選んだモデルの成果物が検証でFAILし続ける場合、その行の割り当てを1段階上げることを検討し、`memory/lessons.md` に記録する。
- 逆に、opus割り当てのタスクがsonnetでも安定してPASSしている実績が溜まったら、割り当てを下げてコストを削減する。
