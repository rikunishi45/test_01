# Model Routing（モデル振り分け）

タスクの性質に応じてモデルを振り分けるための規約。**割り当ての実体は `.claude/agents/*.md` と `.claude/skills/*/SKILL.md` の `model` frontmatter にあり、このファイルはその根拠と例外運用を定める。**

---

## 基本方針

| 役割 | モデル | 理由 |
|------|--------|------|
| Supervisor（メインセッション） | **Opus 5** | 計画・委任・レビュー判断・エスカレーション判断。下流全体に影響するため推論の深さが必要 |
| 実行（実装・リサーチ・検証・ドキュメント） | **Sonnet 5** | 品質とコストのバランスが最良。受け入れ基準が明文化されていればここで十分 |
| 単純作業（ファイル検索、定型ルーブリック採点） | **Haiku 4.5** | 判断がほぼ不要。速度とコストが優先 |
| Fable 5 | **既定では使わない** | 後述「Fable 5 の扱い」を参照 |

メインセッションのモデルは `/model opus` で設定する。設定は user settings に保存されるため、以降のセッションもOpus 5で開始する。

---

## モデルはどこで決まるか

Claude Code のサブエージェントのモデル解決順序（公式仕様、優先度順）：

1. `CLAUDE_CODE_SUBAGENT_MODEL` 環境変数 — **このプロジェクトでは設定しない**（全サブエージェントを一律上書きしてしまい、振り分けが無効になるため）
2. Agentツールの `model` パラメータ（呼び出しごとの上書き）— 例外時のみ使う
3. `.claude/agents/*.md` の `model` frontmatter — **通常はここで決まる**
4. メインセッションのモデル（＝ inherit。frontmatterに `model` が無い場合の既定）

スキル（`.claude/skills/*/SKILL.md`）の `model` はメインセッションのモデルを**そのターンの間だけ**上書きする。設定には保存されず、次のプロンプトでセッションのモデルに戻る。

この設計により、Supervisorが `model` の指定を忘れても各エージェントは自分のモデルで起動する。指定漏れが全部Opus 5に落ちる事故は起きない。

## 割り当て表

| タスクの種類 | 担当 | モデル | 定義場所 |
|------------|------|--------|---------|
| 実装・バグ修正・リファクタリング・テスト作成 | `coder` エージェント | sonnet | `.claude/agents/coder.md` |
| リサーチ・情報の統合・ライブラリ評価 | `researcher` エージェント | sonnet | `.claude/agents/researcher.md` |
| コード・計画・リサーチの検証（Verifier役） | `verifier` エージェント | sonnet | `.claude/agents/verifier.md` |
| ドキュメントの定型ルーブリック採点 | `doc-verifier` エージェント | haiku | `.claude/agents/doc-verifier.md` |
| ファイル検索・広範囲のgrep | 組み込み `Explore` エージェント | haiku（呼び出し時に指定） | Agentツールの `model` パラメータ |
| 計画立案・タスク分解 | `planning` スキル | opus | `.claude/skills/planning/SKILL.md` |

| 曖昧な要件の分解・トレードオフ判断・エスカレーション判断 | Supervisor が直接 | opus（セッションのモデル） | — |

## 運用ルール

1. **委任時にモデルを指定しない。** `subagent_type` でエージェントを選べば、モデルはそのエージェントのfrontmatterで決まる。
2. **`model` パラメータでの上書きは例外時のみ。** 上書きしたら理由を `state/tasks/T-NNN.md` の備考に残す（例：「verifierをopusに昇格：セキュリティ境界の判定のため」）。
3. **ExecutorとVerifierのモデルを揃える必要はない。** 基準が明文化されていれば、下位モデルが上位モデルの成果物を検証してよい。
4. **同一タスク内でのモデル昇格は1回まで。** 段階的に上げ続けるのはコストの無駄。最初から適切な担当を選ぶ。
5. **組み込みエージェント（`Explore` / `Plan` / `general-purpose`）を使う場合のみ、`model` を明示する。** これらはfrontmatterを持たないため、指定しないとメインセッション（Opus 5）を継承する。

## Fable 5 の扱い

Fable 5 はサブエージェントの `model` 値として指定可能だが、**このプロジェクトでは既定で使わない。**

- 現在の契約では Fable 5 はサブスクリプションの利用枠外で、**usage credits（従量課金）で動作する**。Max プラン／プレミアムシートではプラン標準（週次上限の最大50%まで追加費用なし）だが、Pro・Team標準シートではクレジット消費となる。
- Fable 5 は1リクエストが数分〜十数分走る設計のため、1回の委任でもクレジット消費が大きい。長時間稼働するSupervisorセッションをFableにすると、待機時間を含めて課金され続ける。
- **未検証：** クレジット枯渇時にサブエージェントの `model: fable` 指定がどう扱われるか（フォールバックするか失敗するか）は公式ドキュメントに記述がない。組織の許可リストで除外された場合は「継承モデルに静かにフォールバックする」と明記されているが、クレジット枯渇はそれとは別の事象。

**使う場合の条件：** 単発の難問（大規模移行、原因不明の障害調査、アーキテクチャ選定）に限り、ユーザーの明示的な指示を得てから、そのタスク単位で `model: fable` を指定する。routing表への恒久的な組み込みはしない。

## 見直しのタイミング

- 割り当てどおりのモデルの成果物が検証で繰り返しFAILする場合、そのエージェントの `model` を1段階上げることを検討し、`memory/lessons.md` に記録する。
- 逆に、上位モデル割り当てのタスクが下位モデルでも安定してPASSする実績が溜まったら、割り当てを下げてコストを削減する。
- モデルのエイリアス（`opus` / `sonnet` / `haiku` / `fable`）は常に各ファミリの**最新版**に解決される。特定バージョンに固定したい場合のみ、フルモデルID（例：`claude-sonnet-5`）を書く。バージョンを直書きすると世代交代のたびに更新が必要になるため、原則はエイリアスを使う。
