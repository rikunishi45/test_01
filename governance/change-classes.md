# 変更クラス

自動マージの可否を、変更の性質から決めるための分類。**このファイルが分類定義の正本。**

判定は `scripts/classify.py` が差分のパスから機械的に行い、`.github/workflows/classify.yml` が
PRごとに実行する。**エージェントの自己申告には依存しない** — 実行者が自分の成果物を採点しないという
`governance/verification.md` の原則を、マージ可否にも適用している。

---

## 分類

| クラス | 対象 | 扱い |
|---|---|---|
| **A** | `README.md`、`memory/`、`state/`、`docs/` | 自動マージ可 |
| **B** | `tests/`、ロックファイル（`package-lock.json` 等） | 自動マージ可 |
| **C** | `.github/`、`.claude/`、`governance/`、`scripts/`、`src/`、`CLAUDE.md` | 人間のレビュー承認が必須 |
| **D** | クラスCと他クラスが混在した差分 | ブロックし、分割を要求 |

**未知のパスはCに倒す（fail closed）。** 新しいディレクトリを作ったとき、分類を決め忘れても
安全側に落ちる。意図的にA/Bにしたい場合は `scripts/classify.py` の `RULES` に追記する。

---

## なぜガードレール自体をCに置くか

`.github/`・`.claude/`・`governance/` は、自動マージの安全性を支えている仕組みそのもの。
ここをA/Bに入れると、**エージェントが自分の制約を緩めるPRを人間の目に触れずにマージできる**。
一度それが起きると、他のすべての対策が同時に無効になる。単一障害点なので、例外を作らない。

`scripts/` も同じ理由でC。分類ロジックと検証スクリプトが入っているため。

---

## なぜDをブロックするか

クラスCの変更とドキュメント修正が1つのPRに混ざると、レビューが必要な変更が
低リスクな変更に紛れて通りやすくなる。差分が大きいほど見落としが増える。
分割を強制することで、レビューの対象を小さく保つ。

---

## 強制の仕組み（多層）

| 層 | 何を止めるか | 破られたときの影響 |
|---|---|---|
| `scripts/classify.py` ＋ `classify.yml` | クラスA/B にのみ自動マージを有効化。D は必須チェックを失敗させる | 自動マージが誤って有効化される |
| `.github/CODEOWNERS` ＋ ルールセット | クラスCのパスに触れたPRはコードオーナーの承認なしにマージできない | サーバー側の壁が消える |
| `.claude/settings.json` の `deny` | エージェントが `gh pr merge` でクラスCを手動マージするのを止める | ローカルの壁が消える |

`deny` ルールは Claude Code の全権限モード（`bypassPermissions` を含む）で有効な唯一の層。
`allow` は緩めるためだけの道具で `bypassPermissions` では無効化されるため、
禁止事項は必ず `deny` 側に書く。

---

## 定義を変えるとき

分類は3か所に写っている。**片方だけ変えると穴が開く。**

1. このファイル（正本）
2. `scripts/classify.py` の `RULES`
3. `.github/CODEOWNERS`

3つを同時に更新すること。CIはこの3者の一致までは検査しないので、
`governance/workflow.md` の振り返りフェーズで確認する。
