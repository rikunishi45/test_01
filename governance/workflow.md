# ワークフロー

自明でないすべてのタスクに適用する標準の実行サイクル。

---

## サイクル全体像

```
Planning（計画）→ Execution（実行）→ Review（レビュー）→ Reflection（振り返り）
```

各フェーズには開始条件・成果物・終了ゲートが定義されている。

---

## フェーズ1：Planning（計画）

**開始条件：** 新しいタスクまたはゴールを受け取った。

**手順：**
1. ゴールを明確化する — 曖昧な場合は、進む前に焦点を絞った質問を1つする。
2. ステップに分解する。各ステップは以下を持つこと：
   - 明確な成果物（ファイル、コード、意思決定、ドキュメント）
   - 受け入れ基準（「完了」をどう判定するか？）
   - 担当スキル（planning / research / coding / review / documentation）
3. 依存関係とクリティカルパスを特定する。
4. 複雑度を見積もる：small（1〜3ステップ）、medium（4〜8）、large（9以上）。
5. largeタスクには、ユーザーが進捗をレビューできる明示的なチェックポイントを設ける。

**成果物：** 計画を反映した `state/current-task.md`。

**終了ゲート：** 計画が書き出され、ユーザー承認（largeタスク）または自己承認（small/mediumタスク）を得ている。

---

## フェーズ2：Execution（実行）

**開始条件：** 計画が承認された。

**手順：**
1. 依存関係を守りながら、ステップを順番に進める。
2. 各ステップの開始前に、該当するスキルファイルを読み込む。
3. 各ステップの完了後、受け入れ基準に対してセルフチェックする。
4. 完了したステップを `state/current-task.md` に反映する。
5. ブロッカーに遭遇したら先に進まず、表面化させる。

**レビューゲート発動条件（実行を一時停止してレビューする）：**
- 不可逆な操作が発生しようとしている
- ステップの出力が曖昧、または確信度が低い
- ステップが見積もりを大幅に超過している
- 前提としていた依存が存在しない、または想定外の挙動をする
- セキュリティに関わる変更全般

**成果物：** 各ステップの成果物（ファイル、コード、意思決定）。

---

## フェーズ3：Review（レビュー）

**開始条件：** ステップが完了した、またはレビューゲートが発動した。

**手順：**
1. `governance/verification.md` の発動条件に該当する成果物は、**検証ループを回す**：別のサブエージェント（Verifier）を起動し、ルーブリックで採点させる（モデルは `governance/routing.md` に従う）。該当しない軽微な成果物はセルフチェックで可。
2. 確認事項：正確性、完全性、先行ステップとの整合性、副作用。
3. コードの場合：セキュリティ問題、意図しないスコープ、テストカバレッジを確認。
4. 判定する：PASS（進行）/ REVISE（Verifierの修正指示付きで再作業、最大2回）/ ESCALATE（人間に確認）。
5. リトライでも解決しなかった失敗は `memory/lessons.md` に記録する。

**エスカレーション基準：**
- 1回の修正後も出力品質が基準を下回り続ける
- タスクが当初のスコープを逸脱している
- 人間の判断が必要な意思決定（`supervisor.md` のエスカレーションルール参照）

---

## フェーズ4：Reflection（振り返り）

**開始条件：** タスクが完了した（全ステップがレビューをPASS）。

**手順：**
1. アーキテクチャや設計の意思決定を含むタスクだった場合、概要を `memory/architecture-decisions.md` に記録する。
2. 失敗・想定外の成功があった場合、`memory/lessons.md` に教訓として記録し、タグ別出現回数を更新する。
3. 同じタグの教訓が2回以上溜まっていたら、該当スキルへの反映案を作成してユーザーに提示する（承認後に更新）。
4. opusを使った場合はその判断が適切だったかを確認し、`governance/routing.md` の見直し材料にする。
5. フォローアップ項目を `state/todo.md` に記録する。
6. 完了した項目を `state/current-task.md` から整理する。

**成果物：** 更新された `memory/` と `state/` ファイル。

---

## 対外ゲート：PR駆動のNotion同期

ローカルのループ（Planning→Execution→Review→Reflection）の完了を、対外的な進捗に接続する。

- コード成果物がレビュー可能な状態（検証PASS）になったら、`feature/TASK-n-...` ブランチを push し、
  `gh pr create --body "Closes TASK-n"` でPRを作成する。→ Notionが自動で **In Review**。
- PRがマージされたら Notionが自動で **Done**（`.github/workflows/notion-sync.yml`）。
- 詳細な規約は `CLAUDE.md` の「プロジェクト固有ルール — PR駆動のNotion進捗同期」を参照。

このゲートは検証ループ（成果物の品質）とは独立した「対外可視化」の仕組みであり、
検証PASS後のReflectionと並行して行う。

---

## チェックポイントプロトコル

チェックポイント付きのタスクでは、`state/current-task.md` に以下の形式を使う：

```markdown
## Checkpoint N — [名前]

**Status:** pending | in-progress | done | blocked
**Deliverable:** [ユーザーが確認・レビューすべきもの]
**Acceptance criteria:** [正しさをどう検証するか]
**Notes:** [想定外の事項]
```

チェックポイントに到達したら：

1. `governance/verification.md` に従って検証する。
2. PASS → `state/current-task.md` の該当チェックポイントを `done`（検証スコア付き）に更新し、ユーザーの指示を待たずに次のフェーズへ自動的に進む。進捗は応答内で簡潔に報告する。
3. FAIL（リトライ2回後）またはエスカレーション条件該当 → 停止してユーザーに報告する。

ユーザーの明示的な承認が必要なのは Planning フェーズの計画承認時のみ（largeタスク）。実行中の各チェックポイントでは停止しない。

---

## タスクサイズの目安

| サイズ | ステップ数 | チェックポイント | ユーザー承認 |
|------|-------|-------------|---------------|
| Small | 1〜3 | なし | 不要 |
| Medium | 4〜8 | タスク終了時 | 任意 |
| Large | 9以上 | 各フェーズ後 | 計画承認時のみ（各フェーズは検証PASSで自動続行） |
