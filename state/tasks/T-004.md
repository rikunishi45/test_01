## ゴール

人間の関与を「計画のサインオフ」と「異常時の介入」に限定し、実装からPR作成・低リスク変更のマージまでをAIが自律実行できる状態にする。安全性は人間の都度承認ではなく、**機械的な壁（CIとリポジトリルール）** で担保する。

## 前提

- ~~private かつ GitHub Free でブランチ保護が使えない~~ → **解消済み（ADR-002）**。2026-07-27 に public 化し、ルールセットAPIが `403` から `[]` になったことを確認。
- `allow_auto_merge: false`、`delete_branch_on_merge: false`（Step 6 で変更）
- 実装コードとテストが未着手。**空のCIは自動マージの根拠にならない**ため、コードが無くても意味のある検査を用意する。

## 変更クラス定義

分類は**エージェントの自己申告ではなく、差分のパスからCIが機械的に判定する**。正本は `governance/change-classes.md`。

| クラス | 判定条件（変更パス） | 扱い |
|---|---|---|
| **A** | `README.md`、`memory/**`、`state/**`、docs系 `*.md` | 自動マージ可 |
| **B** | テスト追加のみ、lint/整形のみ、ロックファイルのピン止め | 自動マージ可（CI全green必須） |
| **C** | `.github/**`、`.claude/**`、`governance/**`、`CLAUDE.md`、`scripts/**`、`src/**` のロジック | 人間必須 |
| **D** | A/B と C が混在する差分 | ブロックし分割を要求 |

**設計上の要点：** `.github/**`・`.claude/**`・`governance/**` をクラスCに置くのは、**エージェントが自分のガードレールを自動マージで弱められないようにするため**。ここを外すと他の全対策が一度に無効化されうる。

## Step 6 実施記録（2026-07-28）

ルールセットを2本に分割して適用した。理由と代替案は ADR-003。

| ルールセット | ルール | bypass |
|---|---|---|
| `main-ci`（19889689） | `deletion` / `non_fast_forward` / `required_status_checks`（進捗台帳の契約検証・エージェント定義と参照の検証・YAML構文・秘密情報スキャン・変更クラス判定 の5件、`integration_id: 15368`） | **なし** |
| `main-review`（19889691） | `pull_request`（`required_approving_review_count: 0` ＋ `require_code_owner_review: true`） | Repository admin（`actor_id: 5`）、`bypass_mode: pull_request` |

リポジトリ設定は `allow_auto_merge: true`、`delete_branch_on_merge: true` に変更済み。

### 検証済みの事実

- `required_approving_review_count: 0` と `require_code_owner_review: true` は独立したフィールドで、同時指定できる。承認数0は「レビュアーは登録されるが承認は不要」の意味で、コードオーナー承認は別枠で強制される。クラスA/B は承認者0人で auto-merge される
- `GET /repos/.../rules/branches/main` で4ルールが両ルールセットから適用されていることを確認
- PR #3 は classify がクラスD判定で正しく fail していた（ルールセット未設定のためマージできてしまった）。判定機構自体は動作している

### 未検証の事項（Step 11 で実測する）

- あるルールセットの bypass actor が、別ルールセットのルールを免除しないこと。公式ドキュメントに明記がない。この分割設計は「管理者はクラスCをマージできるが、CIが赤ければマージできない」ことに依存している

## Step 6 の副作用 — 台帳の自動生成が機能しなくなった

必須チェックを有効にしたことで、`ledger.yml` による `state/progress.md` の自動再生成が動かなくなった。**未解決。**

PR #4（クラスA）の実測で確認した事実：

1. `classify.yml` が `GITHUB_TOKEN` で auto-merge を有効化すると、そのマージによる main への push が**下流のワークフローを起動しない**（`GITHUB_TOKEN` 起因のイベントは新しいワークフロー実行を作らないという GitHub の仕様）。PR #4 マージ後、`push` 起因の実行は0件だった
2. 仮に `ledger.yml` が起動しても、それが作るPRも `GITHUB_TOKEN` 製なので `ci.yml` / `classify.yml` が走らない。必須チェックが永久に「報告待ち」になりマージ不能

つまり台帳の自動生成は、**`GITHUB_TOKEN` とは別のアイデンティティを持つトークンなしには成立しない。** `state/todo.md` の GitHub App 導入は「あると良い」ではなく、**並列開発を始める前提条件**に格上げする。

**暫定対応：** Supervisor が各クラスA PRに `python3 scripts/ledger.py render` の結果を含める。並列開発の開始（Step 11 完了）までブランチは1本なのでコンフリクトしない。

## Step 8 の装着確認（2026-07-28、検証項目5・6）

PR #5 マージ後のセッションで、フックが実際に発火することを実測した。単体実行ではなく、Bashツール経由の実操作で確認している。

| 実行したコマンド | 期待 | 結果 |
|---|---|---|
| `gh pr merge 5 --squash`（クラスC） | deny | **PASS** — 「PR #5 はクラスC…ブロックしました」 |
| `gh pr merge 7 --squash`（クラスA） | allow | **PASS** — gh に到達し `already merged` |
| `git push origin main` | deny | **PASS** — 「`origin` の `main` への直接push（refspec=`main`）」 |
| `git push origin main:refs/heads/main` | deny | **PASS** — 同上（refspec=`main:refs/heads/main`） |
| `git push origin feature/T-004-nonexistent-probe` | allow | **PASS** — git に到達し `src refspec does not match any` |

いずれも対象がマージ済みPR・no-opのpush・存在しないブランチであり、フックが素通りしても副作用が出ない組み合わせを選んでいる。

### この実測で新たに判明したこと

1. **PreToolUse フックは `permissions.deny` のグロブより先に評価される。** `git push origin main` は deny グロブにも一致するが、返ってきたのはフックのメッセージだった。つまり動的判定が静的グロブに優先する
2. **フックは deny グロブの取りこぼしを実際に埋めている。** `git push origin main:refs/heads/main` は `settings.json` の deny リストに存在しない形式だが、フックが refspec を正規化して遮断した。Step 7 の静的リストだけでは通っていた
3. **`permissionDecisionReason` が Claude 側に届くことを確認した。** ブロック理由が本文として返るため、別の書き方での再試行を誘発しない。PR #5 でこのフィールドを追加した判断は正しかった
4. **偽陽性なし。** クラスAのマージと非mainブランチへのpushはどちらも素通りした。フックが通常のfeatureブランチ運用を壊していない
5. `settings.json` の `hooks[].hooks[].if` フィールドの有効性は未確定だが、**両フックとも自身で `tool_name` とコマンド内容を再判定して非該当なら `allow()` する**ため、仮に `if` が無視されて全Bash呼び出しで起動しても動作は正しい。実測でも通常のコマンドは阻害されていない

## Step 14 がブロックされた理由

マージキューは**組織所有リポジトリ専用**で、ユーザー所有リポジトリでは提供されない。API でも確認済み：

```
POST /repos/rikunishi45/test_01/rulesets  （merge_queue ルール）
→ 422 "Invalid rule 'merge_queue'"
```

ADR-002 の「マージキューが無料で利用可能になり」という記述は誤り。public 化では解消しない。解消するには organization へのリポジトリ移管が必要（`state/todo.md` に起票）。

なお classify.yml は `merge_group` トリガーを持たないため、仮にマージキューが使えても必須チェック「変更クラス判定」がキュー内で報告されず、キューが詰まる。移管する場合は classify.yml の改修が前提。

### クラスCの実測で分かったこと（PR #5）

必須チェック5件が全green になった時点で、PR #5 の状態は次のとおりだった。

```
labels: ["class-C"]   autoMergeRequest: none
reviewRequests: []    reviewDecision: ""    mergeStateStatus: CLEAN
```

- `classify.yml` が auto-merge を有効化しなかった点は意図どおり。**これが実際にクラスCを止めている唯一のサーバー側の要素**
- `reviewRequests` が空なのは、唯一のコードオーナーがPRの作成者自身であり、GitHubが作成者にレビューを要求できないため
- `mergeStateStatus` が `CLEAN` なのは、オーナーが `main-review` の bypass actor だから

つまり **`require_code_owner_review` はこのアカウントに対して実質的に何も止めていない。** ADR-003 が予測したとおりで、クラスCに対する実効的な壁は「classify.yml が auto-merge を有効化しないこと」と「ローカルのフック」の2つだけ。前者はエージェントが `gh pr merge` を明示的に叩けば迂回できるため、**フックが唯一の防御**という結論は変わらない。

この構造は GitHub App（`state/todo.md` 優先度：高）を入れるまで解消しない。

## 検証項目7の実測（2026-07-28）— フック迂回が実証された

マージ済みのPR #5（クラスC）を対象に、`gh pr merge` ではなく REST API を直接叩いた。

```
gh api --method PUT /repos/rikunishi45/test_01/pulls/5/merge -f merge_method=squash
→ {"sha":"c9612e4...","merged":true,"message":"Pull Request successfully merged"}
```

**フックは一切発火せず、書き込みメソッドが GitHub API に到達した。** 副作用は出ていない（`origin/main` は `c9612e4` のまま、`mergedAt` も `12:41:34` から変化なし。既にマージ済みのため GitHub が既存の結果を冪等に返した）が、それは**対象が偶然マージ済みだったから**にすぎない。未マージのクラスC PRであれば、人間のレビューを経ずにマージが成立していた。

### なぜ素通りするか

`block_class_c_merge.py` の `match_gh_pr_merge()` は `gh` → （グローバルオプション）→ `pr` → `merge` というトークン列だけを見る。`gh api` は `pr` に一致しないため `None` を返し、`allow()` に落ちる。`settings.local.json` の `Bash(gh api *)` が権限層でも許可しているため、二層とも通過する。

### この穴が意味すること

クラスCに対する実効的な壁は「classify.yml が auto-merge を有効化しないこと」と「ローカルのフック」の2つだけ、という前回の結論が**さらに弱まる**。フックはコマンド文字列を見る防御であり、同じ操作に別の綴りが存在する限り網羅を保証できない（`gh api` のほかに `curl` + `$GH_TOKEN`、GraphQL の `mergePullRequest` 等も同じ性質の経路）。既知の経路を塞ぐ価値はあるが、**「フックがあるから安全」とは言えない。**

サーバー側でエージェントの権限そのものを絞る（GitHub App の別アイデンティティ）以外に、この構造を根本解決する手段はない。`state/todo.md` の GitHub App 導入の優先度は据え置き「高」のままでよいが、根拠がこの実測に更新される。

## classify.yml の two-dot バグ（2026-07-29、検証項目8）

`.claude/settings.json` **1ファイルのみ**を変更した PR #9 が、クラスC ではなく**クラスD**と判定されブロックされた。クラスDは「分割せよ」を要求するが、1ファイルしか変更していないため分割できない。

### 原因

`classify.yml` が two-dot diff で変更ファイルを取得していた。

```
git diff --name-only "$BASE" "$HEAD"     # 誤り
git diff --name-only "$BASE...$HEAD"     # 修正後（PR #10）
```

two-dot は「BASE の状態と HEAD の状態の差」を取る。**PRの作成後にベースブランチが進むと、そのPRが触っていないファイルまで差分に現れる。** PR #9 のケースでは、先にマージされた PR #8 の `state/tasks/T-004.md` が main に入り、それが差分に混入した。

| 差分の取り方 | 検出ファイル | 判定 |
|---|---|---|
| two-dot | `.claude/settings.json` ＋ `state/tasks/T-004.md` | **D** |
| three-dot | `.claude/settings.json` | **C** |

### 影響と評価

- **誤りは安全側に倒れる。** 混入はクラスを上げる方向にしか働かないため、誤って自動マージされることはない
- ただし**ベースが進むたびに正当なPRがブロックされる。** 並列開発を始めた時点で運用が止まる性質のバグだった。今回はPRを2本連続で作ったために偶然表面化した
- `ci.yml` に同種の差分取得はない。`ledger.yml` の `git diff --quiet -- state/progress.md` は作業ツリーの確認なので別物。**バグはこの1箇所のみ**

### 併せて判明した運用上の注意（バグではない）

**クラスCのPRが複数ある状態で1本をマージしても、残りのPRは自動では再判定されない。** `classify.yml` のトリガーは `pull_request` の `opened`/`synchronize`/`reopened`/`ready_for_review` のみで、main への push を含まない。そのため古い判定結果が残る。

PR #10 をマージした後も PR #9 は `class-D` / FAILURE のままで、`baseRefOid` も PR #10 マージ前の SHA を指していた。ブランチに main を merge して push し、`synchronize` を発火させて復帰させた。

トリガーに `push` を足すのは誤った対処（全PRで再実行が走る）。**運用手順として `governance/workflow.md` に書く。Step 9 の対象に追加した。**

## Step 7 追補 — 権限整備（PR #9、2026-07-29）

Step 7 で緩めた範囲は Bash コマンドだけで、受け入れ基準も「push/PR作成が無確認」に限定されていた。**サブエージェント委任は最初からスコープ外**だったため、`CLAUDE.md` が定める Supervisor の標準手順（Medium以上はステップごとに委任）を実行するたびに人間の承認が必要だった。

「広げる」と「絞る」を同一PRで一体に実施した。allow だけ広げると `gh api` の穴が空いたまま自律性が上がるため、分離しない。

| 区分 | 内容 |
|---|---|
| 広げる（allow） | `Agent(coder/researcher/verifier/doc-verifier)`、`gh pr view/list/diff/checks`、`gh run list/view`、`git fetch/switch/checkout/pull`、`python3 scripts/*` |
| 絞る（deny） | `Bash(gh api *)`、`Bash(curl *)` |
| 維持（ask） | `Edit(/.claude/**)` `Edit(/.github/**)` `Edit(/governance/**)` `Edit(/scripts/**)` `Edit(/CLAUDE.md)` — ローカル権限の境界を変更クラスの境界と一致させる |

### 公式ドキュメントで確定した事実

1. **フックはサブエージェント内でも発火する。** 設定ファイルのフックはサブエージェントのツール呼び出しでも動き、入力に `agent_id`/`agent_type` が付く
2. **サブエージェントは親の permission コンテキストを継承する**
3. 評価順序は **deny → ask → allow**。deny はスコープを問わず allow より先に評価されるため、`settings.local.json` の allow を `settings.json` の deny で潰せる
4. **`Write(path)` ルールはファイル権限チェックに一致しない**（起動時に警告が出る）。`Edit(path)` が全ファイル編集ツールをカバーする
5. 公式は「Bash を全面 allow にしてフックで特定コマンドだけ拒否する」構成を推奨しているが、**今回は採らない。** 現在のフックは `gh pr merge` と `git push` しか見ておらず、全面 allow にすると `gh api` や `curl` が無確認で通る。GitHub App 導入後に再検討する

1と2が不明なままなら委任許可は危険だった。この2点により**委任を許可しても防御レベルは下がらない**ことが確定した。

## T-005 の位置づけ（2026-07-29 に決定）

GitHub App は「セキュリティ対策」ではなく、**自律実行を成立させるための前提条件**である。

当初は「フックを `gh api` にも反応させる（つなぎ）→ 後で GitHub App」の順を想定したが、ユーザーの指摘により順序を入れ替えた。理由：

1. つなぎのフック改修は `.claude/**` でクラスCなので人間の承認が必要。**その承認1回を、捨てる予定の実装ではなく根本解決に使うほうが合理的**
2. GitHub App が入るとフックは唯一の防御ではなくなるため、つなぎの網羅性を作り込む価値が薄い
3. 現状の露出は限定的。`classify.yml` はクラスCで auto-merge を有効化しないため、エージェントが明示的にマージを叩かない限りマージされない。Step 11 未完了＝自律運用も未開始
4. **GitHub App は台帳の自動生成停止（Step 6 の副作用）も同時に解決する。** これは現在進行形のブロッカーで、他に手段がない

事後監視モデル（人間が適当なタイミングで進捗を確認し、方向性がずれていたら介入する）は、**監視の窓口が正確であることに全面的に依存する**。その窓口が `state/progress.md` であり、その自動生成が止まっている。手動更新は更新漏れが起き、かつ漏れたことに人間が気づけない。監視されていない間に進む開発ほど、記録が自動である必要がある。

### 前提条件

- **秘密鍵はユーザーが手動でパスワードマネージャに保管する。エージェントは秘密鍵に触れない前提で設計する。** 秘密鍵が読めれば App の権限範囲内で任意のトークンを生成できるため、エージェントには短命の installation token だけを渡す
- App の権限セットはユーザーが調査結果を見てから判断する

### 調査が必要な核心的な問い（researcher に委任する）

一次情報（docs.github.com）のみを根拠とし、推測は [未確認] と明示させる。

1. `PUT /pulls/{n}/merge` と feature ブランチへの push は、同じ App 権限（`contents: write`）を要求するのか。**permission スコープだけで「push可・マージ不可」を分離できるのか**
2. 分離できない場合、App を bypass actor に含めないルールセットで分離できるか。ルールセットの `pull_request` / `required_status_checks` は App トークンのマージAPI呼び出しにも適用されるか
3. **App トークンによる push / PR作成は GitHub Actions を起動するか**（`GITHUB_TOKEN` の制約を回避できるか。台帳自動生成の復旧可否に直結）
4. ユーザー所有（非organization）リポジトリで App を作成・インストールできるか
5. `gh` CLI が App の installation token を受け付けるか。秘密鍵に触れずに短命トークンだけを受け取る運用が成立するか
