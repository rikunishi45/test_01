## ゴール

人間の関与を「計画のサインオフ」と「異常時の介入」に限定し、実装からPR作成・低リスク変更のマージまでをAIが自律実行できる状態にする。安全性は人間の都度承認ではなく、**機械的な壁（CIとリポジトリルール）** で担保する。

## 前提

- ~~private かつ GitHub Free でブランチ保護が使えない~~ → **解消済み（ADR-002）**。2026-07-27 に public 化し、ルールセットAPIが `403` から `[]` になったことを確認。
- `allow_auto_merge: false`、`delete_branch_on_merge: false`（Step 6 で変更）
- 実装コードとテストが未着手。**空のCIは自動マージの根拠にならない**ため、コードが無くても意味のある検査を用意する。

## 変更クラス定義

分類は**エージェントの自己申告ではなく、差分のパスからCIが機械的に判定する**。正本は `governance/change-classes.md`。

| クラス | 判定条件（変更パス） | 扱い |
|---|---|---|
| **A** | `README.md`、`memory/**`、`state/**`、docs系 `*.md` | 自動マージ可 |
| **B** | テスト追加のみ、lint/整形のみ、ロックファイルのピン止め | 自動マージ可（CI全green必須） |
| **C** | `.github/**`、`.claude/**`、`governance/**`、`CLAUDE.md`、`scripts/**`、`src/**` のロジック | 人間必須 |
| **D** | A/B と C が混在する差分 | ブロックし分割を要求 |

**設計上の要点：** `.github/**`・`.claude/**`・`governance/**` をクラスCに置くのは、**エージェントが自分のガードレールを自動マージで弱められないようにするため**。ここを外すと他の全対策が一度に無効化されうる。

## Step 6 実施記録（2026-07-28）

ルールセットを2本に分割して適用した。理由と代替案は ADR-003。

| ルールセット | ルール | bypass |
|---|---|---|
| `main-ci`（19889689） | `deletion` / `non_fast_forward` / `required_status_checks`（進捗台帳の契約検証・エージェント定義と参照の検証・YAML構文・秘密情報スキャン・変更クラス判定 の5件、`integration_id: 15368`） | **なし** |
| `main-review`（19889691） | `pull_request`（`required_approving_review_count: 0` ＋ `require_code_owner_review: true`） | Repository admin（`actor_id: 5`）、`bypass_mode: pull_request` |

リポジトリ設定は `allow_auto_merge: true`、`delete_branch_on_merge: true` に変更済み。

### 検証済みの事実

- `required_approving_review_count: 0` と `require_code_owner_review: true` は独立したフィールドで、同時指定できる。承認数0は「レビュアーは登録されるが承認は不要」の意味で、コードオーナー承認は別枠で強制される。クラスA/B は承認者0人で auto-merge される
- `GET /repos/.../rules/branches/main` で4ルールが両ルールセットから適用されていることを確認
- PR #3 は classify がクラスD判定で正しく fail していた（ルールセット未設定のためマージできてしまった）。判定機構自体は動作している

### 未検証の事項（Step 11 で実測する）

- あるルールセットの bypass actor が、別ルールセットのルールを免除しないこと。公式ドキュメントに明記がない。この分割設計は「管理者はクラスCをマージできるが、CIが赤ければマージできない」ことに依存している

## Step 6 の副作用 — 台帳の自動生成が機能しなくなった

必須チェックを有効にしたことで、`ledger.yml` による `state/progress.md` の自動再生成が動かなくなった。**未解決。**

PR #4（クラスA）の実測で確認した事実：

1. `classify.yml` が `GITHUB_TOKEN` で auto-merge を有効化すると、そのマージによる main への push が**下流のワークフローを起動しない**（`GITHUB_TOKEN` 起因のイベントは新しいワークフロー実行を作らないという GitHub の仕様）。PR #4 マージ後、`push` 起因の実行は0件だった
2. 仮に `ledger.yml` が起動しても、それが作るPRも `GITHUB_TOKEN` 製なので `ci.yml` / `classify.yml` が走らない。必須チェックが永久に「報告待ち」になりマージ不能

つまり台帳の自動生成は、**`GITHUB_TOKEN` とは別のアイデンティティを持つトークンなしには成立しない。** `state/todo.md` の GitHub App 導入は「あると良い」ではなく、**並列開発を始める前提条件**に格上げする。

**暫定対応：** Supervisor が各クラスA PRに `python3 scripts/ledger.py render` の結果を含める。並列開発の開始（Step 11 完了）までブランチは1本なのでコンフリクトしない。

## Step 14 がブロックされた理由

マージキューは**組織所有リポジトリ専用**で、ユーザー所有リポジトリでは提供されない。API でも確認済み：

```
POST /repos/rikunishi45/test_01/rulesets  （merge_queue ルール）
→ 422 "Invalid rule 'merge_queue'"
```

ADR-002 の「マージキューが無料で利用可能になり」という記述は誤り。public 化では解消しない。解消するには organization へのリポジトリ移管が必要（`state/todo.md` に起票）。

なお classify.yml は `merge_group` トリガーを持たないため、仮にマージキューが使えても必須チェック「変更クラス判定」がキュー内で報告されず、キューが詰まる。移管する場合は classify.yml の改修が前提。
