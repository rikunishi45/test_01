## ゴール

`state/tasks/*.md` を変更したPRがマージされたら、人手を介さずに `state/progress.md` が更新される状態にする。GitHub App の installation token を **GitHub Actions 内でのみ**使い、秘密鍵はローカルに置かない。

T-004 Step 6 の副作用で台帳の自動生成が停止しており、現在は Supervisor が各クラスA PRに `python3 scripts/ledger.py render` の結果を手で含めている。手動更新は漏れが起き、かつ**漏れたことに人間が気づけない**。事後監視モデル（人間が任意のタイミングで進捗を確認し、方向がずれていたら介入する）は監視の窓口が正確であることに全面的に依存するため、これは自律運用の前提条件である。

## なぜ Actions 内限定なのか（2026-07-30 の判断）

目的は2つあり、分離できる。

| 目的 | 必要なもの | 本タスクの扱い |
|---|---|---|
| ① 台帳自動生成の復旧 | **Actions内**で App トークンを使えば足りる | **本タスクの対象** |
| ② エージェントのマージ権限をサーバー側で絞る | **ローカル**のエージェントが App トークンを使う必要がある | Out of Scope。①の動作を見てから判断 |

installation token の有効期限は1時間で、再発行には秘密鍵で署名したJWTが必要。ローカルのエージェントに使わせると「1時間ごとに人が再発行する」か「エージェントが鍵にアクセスできる場所に置く」のどちらかになる。**Actions内なら1ジョブで使い切るのでこの問題が発生しない。** ①は現在進行形のブロッカーであり、秘密鍵をローカルに置かないためリスクも小さい。

## 前提（調査で確定した事実、2026-07-30）

一次情報（docs.github.com）で確認済み。各項目の出典は後述の「調査記録」に列挙する。

- **PR作成とマージは同一スコープ**（`Pull requests: write`）。「PR作成可・マージ不可」は permission だけでは分離できない
- **push は `Contents: write`** で、マージとは別スコープ
- **App トークンによる push / PR作成は下流ワークフローを起動する**（`GITHUB_TOKEN` の制約を回避できる）。公式に明記あり
- **ユーザー所有（非organization）リポジトリでも App を作成・インストールできる**。organization 限定の制約はない
- **installation token の有効期限は1時間**
- ルールセットは「CIが緑で承認が揃うまでマージさせない」という**条件付き抑止**までで、「App は永久にマージできない」という恒久禁止はできない。**これは受容済み**（2026-07-30 にユーザーが意図どおりと確認）

### 恒久禁止できない点を受容する理由

App 化の最大の獲得は「PR作成者が `xxx[bot]` になることで CODEOWNERS が実際に機能する」ことである。現在は作成者＝唯一のコードオーナーのため GitHub が承認を要求できず、`require_code_owner_review: true` が何も止めていない（T-004 の実測）。App 化でクラスCは実際に承認待ちになる。クラスA/BがCI green後にマージされるのは望ましい動作である。

### Step 5 を1本のPRにまとめる理由

`ledger.yml` と `classify.yml` はどちらも `.github/**` でクラスCになる。別PRに分けると、片方をマージした時点でもう片方が再判定されず古い結果のまま残る（`classify.yml` のトリガーに main への push が無いため。T-004 で実測済み）。**同一PRにまとめる。**

### Step 2・3 は不可逆区間（復旧手段を先に決めておく）

どちらも共有インフラ（リポジトリへの App installation、CI Secrets）への変更で、グローバルルールの「共有インフラのデプロイや変更」に該当する。**担当がユーザーであることを理由に無検証で通さない。** CP2 で確認する。

| ステップ | 変更対象 | 復旧手段 |
|---|---|---|
| 2 | App の作成とインストール | インストールを解除する。App 自体の削除も可能 |
| 3 | `APP_ID` / `APP_PRIVATE_KEY` の登録 | Secrets を削除する。鍵が漏れた疑いがあれば App 側で鍵をローテーションし、Secrets を再登録する |

どちらも可逆だが、**秘密鍵は生成直後にしかダウンロードできず、後からUIで読み出せない。** ユーザーはパスワードマネージャ側に原本を保管しておく必要がある（保管しないまま Secrets だけに入れると、以後のローテーション以外に復旧手段がなくなる）。

### Step 4 を独立させる理由

`gh` CLI のサブコマンドが installation token で動くかは**未確認**である。`gh pr view` / `gh pr merge` が GraphQL 経由で `Resource not accessible by integration` になる報告がコミュニティにあり、公式には改善済みとされるが確証がない。ここで動かなければ Step 5 の実装方針が変わる（REST API 直叩きに切り替える等）ため、実装前に切り分ける。

  └→ 2（App作成）→ 3（Secrets登録）

## Checkpoints

- **CP1（Step 1 後・サインオフ）** — 権限セットの決定。過剰な権限を与えていないかの判断はユーザーに委ねる
- **CP2（Step 3 後）** — 不可逆区間の終端。App が意図した権限でインストールされ、Secrets が2件登録されていることを確認する。ここまでで問題があれば、先に進む前にインストール解除で戻す
- **CP3（Step 4 後）** — `gh` CLI が App トークンで動くことの確認。**動かなければ設計変更**なので、ここで止めて報告する
- **CP4（Step 6 後・サインオフ）** — 台帳自動生成の復旧を確認し、暫定対応を撤去してよいか判断する

## 権限スコープの提案（Step 1 で確定する）

| スコープ | レベル | 必要理由 |
|---|---|---|
| `Contents` | Read and write | `ledger.yml` が `state/progress.md` を更新するブランチを push する |
| `Pull requests` | Read and write | `ledger.yml` のPR作成と、`classify.yml` の auto-merge 有効化 |

これ以外に必要なものは Step 4 のスパイクで判明する。**必要最小から始めて、足りなければ足す**方針とし、最初から広く与えない。

### 一次情報が得られなかった主張（設計の根拠には使わない）

以下はコミュニティの回答のみで、公式ドキュメントの裏付けが取れなかった。**採用しない。**

- 「`Pull requests: write` は `Contents: write` に暗黙依存する」— community/discussions/190713。公式のエンドポイント対応表とは矛盾する。本タスクは両方を付与するため影響しない
- 「非同期の auto-merge 完了パスでは bypass_actors が再チェックされないケースがある」— community/discussions/136531。Step 6 の実測で観察する
- 「installation token では `gh pr view` / `gh pr merge` が `Resource not accessible by integration` になる」— cli/cli/discussions/8083。**Step 4 のスパイクで実測する**（これが Step 4 を独立させた理由）

## Out of Scope

- **ローカルのエージェントに App トークンを渡すこと**（Keychain 経由の発行スクリプト、または machine user ＋長命PAT）— 目的②。①の動作を見てから別途判断する
- **organization へのリポジトリ移管** — マージキュー（T-004 Step 14）の解消手段だが本タスクとは独立
- **クラスCのマージ抑止をサーバー側で恒久化すること** — 調査の結果、ルールセットでは実現できない。受容済み
- **ローカルのフックの撤去** — App 化後もフックは残す。多層防御として機能する
